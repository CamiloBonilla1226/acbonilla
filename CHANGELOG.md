Todas las decisiones técnicas relevantes y funcionalidades implementadas en el proyecto base se registran aquí, en orden cronológico.

## 2026-09-24
- Se inicializó el proyecto con Vite + React (plantilla `react`, JavaScript sin TypeScript, siguiendo el stack que ya usan los documentos de contexto).
- Se creó la estructura de carpetas definida en `contexto-proyecto-base.md`: `components/{layout,menu,carrito,promociones,admin}`, `hooks`, `lib`, `pages/admin`, `config`.
- Se creó `src/lib/supabaseClient.js`, leyendo `VITE_SUPABASE_URL` y `VITE_SUPABASE_ANON_KEY` desde variables de entorno, y `.env.example` con las variables de ejemplo (sin valores reales).
- Se creó `src/config/negocio.config.js` con un `negocioId` de ejemplo y los campos de marca (colores, tipografía, WhatsApp) que cada negocio clonado debe personalizar.
- Se implementó `src/lib/phoneAuth.js` con la transformación número → correo interno. Decisión: el correo interno combina `numero` + `negocioId` (no solo el número), porque `numero` es único por negocio pero todos los negocios comparten el mismo `auth.users` de Supabase, y un correo basado solo en el número podría colisionar entre dos negocios distintos con dueños que tengan el mismo teléfono.
- Se implementó el hook `useAuth` (login por número + contraseña, sesión reactiva vía `onAuthStateChange`, roles `dueño`/`empleado` leídos de `user_metadata`). Se agregó una verificación adicional en el login que cierra la sesión si el `negocio_id` de la sesión no coincide con el `negocioId` configurado en este proyecto — no es la seguridad real (esa la aplica RLS), pero es una capa extra de defensa en profundidad acorde a las buenas prácticas pedidas en el brief.
- Se implementaron `useCategorias`, `useProductos` y `usePedidos`, cada uno con fetch + CRUD (los tres se reutilizarán tanto en las pantallas públicas de solo lectura como en el panel admin; las políticas de RLS son las que realmente restringen qué operaciones puede completar cada usuario).
  - `useProductos` trae cada producto con su categoría y sus `grupos_opciones`/`opciones` anidados en una sola consulta (select anidado de Supabase), reflejando el modelo exacto documentado.
  - `usePedidos` incluye una suscripción opcional a Supabase Realtime (`tiempoReal: true`) filtrada por `negocio_id`, para que el panel admin muestre pedidos nuevos sin necesidad de recargar — está pensado para usarse en la pantalla de Pedidos del punto 8, no en el checkout público.

  - `useCarrito`: agrupa por `producto_id` + combinación exacta de opciones elegidas (mismo producto con las mismas adiciones se acumula en una sola línea con cantidad mayor, en vez de duplicar filas).
  - `Checkout.jsx` valida en el cliente (nombre, teléfono, dirección no vacíos) y además sanitiza el teléfono a solo dígitos antes de guardarlo — pero la validación real de integridad de datos sigue dependiendo de las restricciones y RLS de la base de datos, tal como pide el brief.
  - El link de WhatsApp se arma con `lib/whatsapp.js` a partir del detalle exacto del carrito, después de guardar el pedido en Supabase (se guarda primero para no perder el pedido si el usuario cierra la pestaña de WhatsApp sin confirmar el envío).
  - **Decisión pendiente de tu confirmación**: el modelo de datos documentado en `contexto-proyecto-base.md` no incluye una columna de imagen en `productos` (solo `id, categoria_id, nombre, descripcion, precio, precio_oferta, disponible, creado_en`). Como el brief sí exige "carga de imágenes optimizada" para el catálogo, construí `ImagenProducto` y `ProductoCard` asumiendo una futura columna `productos.imagen_url` (texto, URL de la imagen). Si el nombre real de la columna es distinto, avísame para ajustarlo.

Es una decisión de UX no explícita en el brief: permite que el cliente sepa que el producto existe normalmente, en vez de que desaparezca sin explicación.
- Se construyó el panel admin completo (punto 8): `Login`, `Dashboard`, `Productos`, `Pedidos`, `Usuarios`, con rutas protegidas (`RutaProtegida`) que redirigen a `/admin/login` sin sesión, y a `/admin/pedidos` si un `empleado` intenta entrar a una ruta `soloDueno` (Productos, Usuarios). Esto refuerza en la interfaz lo que ya aplican las políticas de RLS — no las reemplaza.
  - Se agregaron dos hooks no listados originalmente en el brief, siguiendo el mismo patrón fetch + CRUD que los demás: `useGruposOpciones` (adiciones/variantes por producto) y `useUsuariosAdmin` (listar/crear/eliminar cuentas del panel). Eran necesarios para cumplir "gestión de ofertas y adiciones" y "gestión de usuarios empleados" del punto 8.

## 2026-09-24 (3)
- **Corrección de seguridad**: se detectó que las políticas RLS usaban `auth.jwt() -> 'user_metadata' ->> 'negocio_id'` para identificar el negocio de cada usuario admin. El problema es que `user_metadata` lo puede modificar el propio usuario autenticado con `supabase.auth.updateUser()` desde el navegador — cualquier admin podría haberse cambiado a sí mismo el `negocio_id` y accedido a datos de otro negocio. Ya se corrigieron del lado de la base de datos las 6 políticas afectadas (categorías, productos, grupos_opciones, opciones, y las dos de pedidos) y las políticas del bucket de Storage, todas usando `app_metadata` en su lugar. `app_metadata` no se puede escribir desde el navegador bajo ninguna circunstancia, solo desde un servidor con la `service_role` key.
  - Esto dejó obsoleta la implementación de `useAuth` (leía `rol`/`negocio_id` de `user_metadata`) y la de creación de empleados (`lib/adminClient.js`, un segundo cliente Supabase en el navegador haciendo `signUp` con esos datos en `user_metadata` — nunca iba a poder escribir en `app_metadata`).
  - **`useAuth.js`**: ahora lee `rol`/`negocio_id` de `session.user.app_metadata` en vez de `user_metadata`, tanto en la sesión reactiva como en la verificación adicional del login.
  - **Nueva Edge Function `supabase/functions/crear-usuario-admin/index.ts`**: corre en el servidor de Supabase (Deno), es la única pieza del proyecto con acceso a la `service_role` key. Recibe `numero`, `contrasena` y `rol`; identifica a quien la invoca a través de su JWT (no del body) y exige que sea un `dueño` autenticado; toma el `negocio_id` del propio `dueño` que llama (nunca de lo que mande el cliente, para que ni por error ni por manipulación del body se pueda crear un usuario para otro negocio); crea el usuario con `auth.admin.createUser()` y le asigna `app_metadata: { negocio_id, rol }` con `auth.admin.updateUserById()`. Si ese segundo paso falla, revierte creando y borrando el usuario para no dejar una cuenta a medias que nunca pasaría el RLS.
  - **`lib/adminClient.js` se eliminó** (ya no tiene ningún uso).
  - **`useUsuariosAdmin.js`**: `crearEmpleado` ahora llama a `supabase.functions.invoke('crear-usuario-admin', { body: { numero, contrasena, rol: 'empleado' } })` en vez del `signUp` con el segundo cliente; si la función responde éxito, sigue insertando la fila en `usuarios_admin` igual que antes (eso no cambió, solo la forma de crear la cuenta de Auth).
  - **Pendiente de tu parte para poder probar el flujo**: desplegar la función con `supabase functions deploy crear-usuario-admin` (usando el CLI de Supabase, autenticado contra tu proyecto). Las tres variables que la función necesita (`SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`) las inyecta Supabase automáticamente en el entorno de toda Edge Function — no hay que configurarlas a mano.
  - **Nota**: como todavía no hay ningún usuario `dueño` creado, el primer usuario dueño de cada negocio necesariamente se crea manualmente (ej. desde el SQL editor o el dashboard de Supabase Auth, asignándole `app_metadata: { negocio_id, rol: "dueño" }` a mano) — esta Edge Function sirve para que ese dueño, ya autenticado, cree después a sus empleados. Avísame si quieres que dejemos documentado ese paso manual del primer dueño en el README.

## 2026-09-24 (4)
- **Lección aprendida — login fallaba con 400 aunque el usuario dueño estaba bien creado en Supabase**:
  - **Problema**: al probar el login del primer usuario dueño (creado manualmente en Supabase, con `app_metadata.negocio_id` y `app_metadata.rol` correctos), `signInWithPassword` devolvía un error 400 "Bad Request".
  - **Causa**: `src/config/negocio.config.js` todavía tenía el `negocioId` de ejemplo por defecto (un UUID placeholder), en vez del `negocio_id` real del negocio de prueba. El correo interno que arma el login (`numeroACorreoInterno`, ver `lib/phoneAuth.js`) se construye con el `negocioId` de este archivo de configuración, no con un valor que el usuario escribe. Como ese `negocioId` no coincidía con el usado al crear el usuario en Supabase Auth, el correo generado no correspondía a ninguna cuenta real — de ahí el 400, que en apariencia parece un problema de credenciales pero en realidad es un desajuste de configuración.
  - **Solución**: actualizar `negocio.config.js` con el `negocioId` real antes de cualquier intento de login de prueba.
  - **Lección para el futuro**: cada vez que se clone este proyecto base para un negocio nuevo, o se pruebe el login de un usuario admin recién creado, el primer paso a verificar (antes de sospechar de la base de datos o de RLS) es que `negocio.config.js` tenga el `negocioId` correcto. Un placeholder sin reemplazar produce exactamente este mismo error 400 engañoso.
  - **Mitigación agregada**: `negocio.config.js` ahora exporta el UUID placeholder original como constante (`NEGOCIO_ID_EJEMPLO`) y `src/lib/supabaseClient.js` compara `negocioConfig.negocioId` contra ese valor al arrancar, emitiendo un `console.warn` explícito si coinciden, para que este error deje de diagnosticarse a ciegas.

## 2026-09-24 (5)
- **Corrección de seguridad/datos — RLS activado sin políticas en `usuarios_admin`**:
  - **Síntoma**: al crear el primer empleado desde el panel admin, el frontend recibía `{"code": "42501", "message": "new row violates row-level security policy for table \"usuarios_admin\""}`. Al reintentar con el mismo número, la Edge Function `crear-usuario-admin` respondía "Ya existe un usuario con ese número en este negocio.", aunque el dueño no veía ningún empleado nuevo en el panel.
  - **Causa raíz**: la tabla `usuarios_admin` tenía `enable row level security` desde el script original, pero nunca se le crearon políticas. Con RLS activado y cero políticas, Postgres bloquea por defecto toda lectura y escritura para cualquier rol que no sea `service_role`. La Edge Function sí lograba crear el usuario en `auth.users` con su `app_metadata` correcta (usa `service_role`, que ignora RLS), pero el insert posterior en `usuarios_admin` —hecho desde el frontend con la sesión normal del dueño— sí pasaba por RLS y fallaba. Resultado: un usuario "fantasma", creado en Auth pero sin fila en `usuarios_admin`, indetectable desde el panel pero que bloqueaba reintentos con el mismo número.
  - **Solución aplicada directamente en Supabase**: se crearon las 4 políticas faltantes para `usuarios_admin`, con el mismo patrón de `app_metadata` que ya usan el resto de tablas: `select` (cualquier admin del negocio ve a sus compañeros), `insert`/`update`/`delete` (solo `rol = 'dueño'`, y siempre limitado a su propio `negocio_id`). Se limpiaron manualmente los usuarios fantasma que habían quedado de las pruebas fallidas.
  - **Cambio de diseño para que esto no se repita**: se movió el insert en `usuarios_admin` de `useUsuariosAdmin.js` (frontend, sujeto a RLS) hacia dentro de la propia Edge Function `crear-usuario-admin` (usa el cliente `service_role`, que ya estaba disponible ahí para crear el usuario de Auth). Ahora crear un empleado es una sola operación en el servidor: si el insert en `usuarios_admin` falla por cualquier motivo, la función revierte borrando el usuario de Auth recién creado — el mismo patrón de rollback que ya existía para el fallo de `app_metadata`. Un fallo a mitad de camino ya no puede dejar un usuario a medias. `useUsuariosAdmin.js` (`crearEmpleado`) ahora solo invoca la función y recarga la lista.
  - **Revisión de otros usos de `usuarios_admin`**: es la única tabla con ese nombre referenciada en el código, y `useUsuariosAdmin.js` es el único archivo que la toca. `recargar` (select) y `eliminarUsuario` (delete) no cambiaron — ya dependían de RLS y ahora quedan cubiertos por las políticas nuevas; se probaron manualmente después de aplicar las políticas y funcionan correctamente (listar empleados del negocio, y que un dueño pueda eliminarlos). No existe todavía una función de edición de usuarios en el panel, aunque la política de `update` ya está creada para cuando se implemente.
